# 预置技能簇

> **技能不按学科组织。** 「复盘方法」属于哪个学科？没有答案。所以技能不进
> `graph/`（学科骨架），而在这里按**能力簇**分组。这是三实体模型的落点：
>
> ```
> 知识 know-what  points/         按学科组织      衰减快    「知道」
> 技能 know-how   experience/skills/  按能力簇      衰减慢    「会做」
> 经验 know-when  experience/     按情境          不衰减    「做过」
> ```
>
> 技能是**中转站**：向上连知识点（`requires`），向下连经验（`experience`，
> 存项目名而不是 id——字段定义见 `_meta/schema.md` 技能段）。

---

## 文件格式

一个文件 = 一个能力簇，标题即簇名，列表项即技能：

```markdown
# 人际沟通

- 结构化表达〔tacit〕
- 信息检索〔composite〕
```

`〔〕` 里是 `kind`：

| kind | 含义 | `requires` 该不该有 |
|---|---|---|
| `composite` | **可分解**：由若干知识点支撑 | 应该有，没有就是缺采集 |
| `tacit` | **隐性手感**：不可命题分解 | 允许为空，不是缺数据 |

没写 `〔〕` 按 `composite` 处理。

---

## 为什么 `requires` 不预置

预置「结构化表达 requires 某某知识点」等于凭空造边——那两个知识点是**谁**的？
技能与知识的连边只能长在**具体用户的档案**里，由 agent 建议、用户确认，或者
由行为证据反推（`ingest.py --target A --target B` 的共现）。

本目录只提供**名字**，不提供边。

---

## 用户侧怎么用

`skill.py --seed` 会把本目录里的技能抄进 `users/<id>/experience/skills/`，
熟练度从 0 起——**没有行为证据就是 0，不因为你「应该会」而给分**。
这是知识分与技能分互不推导的落点。
