## 5. 提问时的流程（核心使用时刻）

```
用户提问
  │
  ├─ ⓪ 先判断该不该走本流程：
  │     纯事务请求（写邮件/翻译/算数）→ 直接办，结束，不查档案
  │     任何讲解/教学/咨询/复盘类  → 继续往下
  │
  ├─ ⓪' 档案存在吗？不存在 → 先正常回答，末尾顺带问背景（话术见 `onboarding.md` §0.2）
  │
  ├─ ① python3 scripts/query.py --user <id> --q "<问题>"
  │
  ├─ ② 按返回的知识点状态决定讲解深度
  │     untouched   → 当全新知识讲，完整铺垫
  │     aware       → 补背景再进主题
  │     understood  → 默认知道原理，重点讲怎么用、有什么坑
  │     applicable  → 默认你会用，直接进深水区与边界
  │     proficient  → 只讲增量与例外
  │     rusty       → "这个你以前深入过，有段时间没碰了"
  │                    先一句唤醒，再展开
  │
  ├─ ③ 有 Playbook → 按其流程处理，并说明来源（哪次项目）
  ├─ ④ 有智慧原则 → 套用
  ├─ ⑤ 按 D 轨特征调整表达（要例子？要结论先行？）
  │
  ├─ ⑥ 正常回答
  │
  └─ ⑦ 写入 E 轨日志；本次暴露遗忘 → 记负向证据

  ── 附加：拿不准时主动咨询 ──
  背景不足 / 推断有歧义 / 跨学科关联不确定
    → 走 `onboarding.md` §0.6（科目选项、掌握程度、能力信息、学习目标）
    → 咨询结果写入档案，调整推断权重
```

> `query.py` 返回六段：知识点状态 / Playbook / 智慧原则 / **横向关联** / **相关技能** / 画像特征。
> 后三段是 3.5.0 新增——横向关联告诉你「他还在什么地方用过这个概念」，
> 相关技能告诉你「他手上会不会做」，别只读第一段。

### 节流规则（防止这套系统反噬对话质量）

- **同一次回答只查一次档案**，不要为每个子问题重复查询
- **同一会话内同一知识点只记一条证据**，合并 note
- 查询/写入失败 → **不阻塞回答**，正常答完，末尾一句说明
- 档案状态与问题无关时（用户问的是全新领域）→ 仍要查一次，
  但要用来判断"这是他的盲区"而非硬套深度

### 5.1 网络知识推断

当用户提及网络资源、文献、网页或外部知识时：

1. **抓取关键概念**：从网址、文献或描述中提取核心知识点
2. **结合用户背景**：按已录入的学历、职业、区域过滤并调整置信度
3. **生成推断项**：`origin: inferred`、w=5 起步；经用户确认后升级为 `user_confirmed`
4. **写入证据**：记录来源 URL/文献，关联到对应知识点，更新 `raw_score`
5. **背景不足时**：走 `onboarding.md` §0.6 主动补充咨询，不自行猜测
6. **落到落地**：条数多时直接走 `expansion.md` 的 `expand_profile.py`（模式 B 则手工落盘）

> **与 `expansion.md` 的分界**：本节是「一次对话里顺手抽几条」，
> `expansion.md` 是「按背景逐面检索、批量灌库」。条数超过 10 条就该换后者。

## 7. 生成报告

```bash
python3 scripts/report.py --user <id>                # 终端摘要
python3 scripts/report.py --user <id> --save         # 落盘 users/<id>/reports/
python3 scripts/report.py --user <id> --subject 数学   # 单学科
```

八节：总体概览 / 域分布（广度 × 深度）/ 掌握度分层 / 正在生疏 / 盲区提示 /
待验证与待确认 / 近期动态 / **技能与错位**。

刻意设计（**回答用户时也要守住**）：
- **全库均值与已触及均值并列**：全库均值把未触及项计入分母会显得很低，
  两个都给，避免用户误读为"我很差"
- **盲区按「你已有积累的学科」优先排序**：数学的核心知识点没学，
  对前端不重要；计算机科学里的才是真缺口
- **未触及的域折叠成一行**：骨架全铺保证了「位置一直在」，
  但展示时必须折叠，否则报告会被一排 0% 淹没（原则 B）
- **先验与实测视觉分离**：`prior_exposure` 推出的「待验证清单」
  必须标注为**猜测**，绝不能与 `raw_score` 混在一张表里
- **没有行为证据的技能折在簇里**：23 个技能全列出来是一面 0 分的墙，
  但它们确实存在。折叠成「人际沟通 8 个」比删掉或全列表都好
- **gap 只说方向，不判人**：说「这个技能你手熟但原理淡了」，
  不说「你的理解很浅」

## 9. 交互规范

### 9.1 必须确认的时机

- 推断出一批知识点 → **批量**轻量告知，不逐条问
- 命中多条相似知识点 → 确认是哪一条
- 记负向证据 → 用中性表述，避免"扣分"感
- 归档或删除 → 二次确认
- **改系统** → 走 `improving.md` §8 完整流程

### 9.2 输出模板

| 场景 | 模板 |
|---|---|
| 冷启动完成 | 铺了多少条 → 哪几块把握较高 → 如何修正 → 后续怎么补 |
| 查看分布 | 域 × 广度/深度 → 强项 → 盲区 → 待验证清单 → 正在生疏 Top N |
| 提问命中 rusty | 一句唤醒 → "你当时是在 XX 场景下掌握的" → 再展开 |
| 同类事件 | 调出 Playbook → 说明来源（哪次项目）→ 按流程推进 |

### 9.3 语气红线

- **禁止评判性表述**：不说"你这方面很弱"，说"这块的证据还比较少"
- **遗忘中性化**：不说"你忘了"，说"这个有一段时间没碰了"
- **推断透明**：任何推断必须可追溯到依据
- **不夸大**：库里没有就说没有，不编造未命中的内容
