## 8. 系统改进机制（用户提改进建议时必走）

> **核心原则：用户对系统本身的建议，先验证、再确认、最后才改。**
> 禁止接到建议就直接动手。理由：本系统的配置会影响所有已积累数据，
> 一次草率修改可能让整个档案失真，且用户难以察觉。

### 8.1 识别触发信号

| 类型 | 例子 |
|---|---|
| 直接建议 | "这个权重应该调高"、"能不能加一个 XX 功能" |
| 指出问题 | "这个判定不对"、"算出来的分数不合理" |
| 质疑规则 | "为什么半衰期是 90 天"、"凭什么推断权重这么低" |
| 表达偏好 | "我希望报告里能看到 XX" |

**注意区分**：用户说"这条知识点标错了"属于**数据纠错**（走 `recording.md` §6.5，直接改），
不属于系统改进。判断标准是——改的是**一条数据**，还是**规则本身**。

### 8.2 五步流程

```
① 复述确认理解
② 判断改动层级 + 验证可行性
③ 向用户确认（带影响说明与回滚方案）
④ 执行修改（先备份）
⑤ 记录 CHANGELOG 并验证生效
```

#### ① 复述确认理解

> 我理解你的意思是：把「自评」的权重从 8 提到 15，
> 因为你觉得自评其实比系统推断可靠。是这样吗？

#### ② 判断改动层级并验证

| 层级 | 范围 | 风险 | 验证方式 |
|---|---|---|---|
| **L1 配置** | `_meta/*.md` 数值 | 低 | 改完跑一次 report 对比前后 |
| **L2 数据** | `graph/` `inference/` | 中 | 在**测试用户**上跑冷启动，看推断结果 |
| **L3 脚本** | `scripts/*.py` | 中高 | 必须回归测试：冷启动→录入→衰减→查询→报告 全链路 |
| **L4 主逻辑** | 公式、状态判定、流程、**文档结构** | **高** | 必须论证+举例说明影响，充分确认后才改 |

**验证必须在测试用户上进行**，禁止直接拿真实用户数据试：

```bash
python3 scripts/init_profile.py --user __test__ --edu "..." --job "..." --region "..."
python3 scripts/report.py --user __test__
# 对比结论后删除：rm -rf users/__test__
```

验证要回答三个问题：改完之后，一个典型用户的分数会怎么变？
有没有副作用？现有数据是否需要重算？

#### ③ 向用户确认

必须包含三要素：**改什么 / 影响什么 / 怎么回滚**。

> 我想这样改：
> - **改什么**：`_meta/weights.md` 中 `self_report` 权重 8 → 15
> - **影响什么**：你已有的 12 条自评记录分数会上升约 5–8 分，
>   其中「项目管理」会从「理解原理」升到「能上手做」。推断类不受影响。
> - **怎么回滚**：这次改动会单独提交一次，`git log` 里能看到，说一句"撤回"我就回滚该提交。
>
> 要改吗？

**风险越高，确认越要充分**。L4 级改动必须举例说明对具体数据的影响，不能只讲概念。

#### ④ 执行修改

1. **先留退路**：本仓库已纳入 git——改动前保持一次干净 `git commit`，
   改完再单独提交一次。回滚 = `git revert <提交>` 或 `git checkout -- <文件>`。
   （**只有 git 表达不了的资产**，如用户数据快照，才放 `archive/`）
2. 执行修改
3. 跑一遍验证：冷启动 → 录入 → 衰减 → 查询 → 报告
4. 确认无破坏后再告知用户完成

#### ⑤ 记录

在 `CHANGELOG.md` 追加一条：

```markdown
## [3.0.1] 2026-10-14
- 改动：self_report 权重 8 → 15
- 层级：L1 配置
- 原因：用户认为自评比系统推断可靠
- 影响：已录入自评记录分数上升，推断类不受影响
- 回滚：git 提交 <hash>（回滚即 revert 该提交）
```

### 8.3 禁止自动修改的情况

- 用户只是抱怨，未提出具体方案 → **先询问期望**，不要替他做决定
- 改动会影响所有用户的已有数据 → 必须确认
- 你不确定用户意图 → 复述并追问
- 用户随口一说、未明确要求改 → 记下来，不立即执行

### 8.4 主动发现问题的义务

日常使用中若发现以下情况，应**主动提出**改进建议（同样走五步流程，不自行修改）：

- 同一个问题连续 3 次匹配不到知识点 → 骨架可能缺项或别名缺失
- 某学科的知识点长期全是 0 分 → 推断模板可能覆盖不足
- 衰减后出现大量不合理 `rusty` → 半衰期档位可能不匹配该学科
- 用户反复纠正同类推断 → 推断规则本身可能有偏差
- **某个子文档被反复读取却从不产生动作** → 它可能该合回主文档或删掉

## 10.1 脚本清单

| 脚本 | 职责 | 模式 B 替代 |
|---|---|---|
| `bootstrap.py` | **入口**。检查档案状态，输出你的下一步动作 | 手工读 `profile.md`（`manual-mode.md`） |
| `init_profile.py` | 冷启动：背景 → 推断 → 铺骨架 → 建档（每个推断分都带一条 `role: seed` 证据） | 手工建 `profile.md` + 推断项 |
| `expand_profile.py` | **联网扩展**：把检索出的知识点灌进档案并写证据（`expansion.md`） | 手工建 points + evidence |
| `ingest.py` | 录入证据并重算分数（支持**多目标**、技能目标、负向证据与 `--verify`） | 手工按 `model.md` §3 公式重算 |
| `decay.py` | 每日衰减，更新状态与遗忘清单 | 手工按 §3.3 推算 |
| `query.py` | 提问时查询：知识点状态 + 横向关联 + 相关技能 + Playbook + 画像 | 手工检索 `points/*.md` 的 name/tags |
| `report.py` | 生成知识分布报告（域折叠 + 广度×深度 + 待验证清单 + 技能错位） | 手工按 `answering.md` §7 八节聚合 |
| `link.py` | **横向边**：共现检测、三档建议、建边/拒边、登记簿 | 手工扫证据共现（`manual-mode.md` ⑦） |
| `skill.py` | **技能实体**：播种/新建/连 requires/gap、项目与 Playbook | 手工建 `skills/*.md`（`manual-mode.md` ⑧） |
| `migrate_s1.py` | 档案迁移（3.4.0）：可读命名 + 字段统一 + 清理旧字段。**幂等、不动分数** | 手工改名与补字段 |
| `migrate_s2.py` | 3.5.0 迁移：证据 `target_ids` 多值化 + 种子 `role` 显式化 + 补录无证据的分 + 重名合并 | — |
| `migrate_s3.py` | 3.5.0 迁移：`职业技能` 49 条改归属（**只改元数据，分数零变化**）+ 播种技能簇 | — |

> 三个 `migrate_*` 都是一次性迁移，但**都幂等**——重跑只会输出「0 条」。
> 它们保留在仓库里，是为了让别的用户也能升级自己的旧档案。

## 10.5 自检清单

**每次回答前**（模式 A / B 通用）：

- [ ] 我跑过启动协议了吗（或手工检查过档案状态）？
- [ ] 这个问题该不该查档案（是纯事务请求吗）？
- [ ] 我拿到知识点状态了吗？讲解深度是按状态定的，还是凭感觉定的？
- [ ] 我要说的内容里，有没有把 `inferred` 当成"用户已掌握"来讲？

**每次会话结束前**：

- [ ] 本次触及的知识点，证据写了吗（同一知识点只写一条）？
- [ ] 一次回答用到多个知识点时，是否用了**一条多目标证据**（共现才有燃料）？
- [ ] 有新增的推断项吗？告知用户了吗？
- [ ] 有暴露遗忘吗？记负向证据了吗（且用中性表述）？
- [ ] 有共现候选吗？提了建议吗（≤3 对、带依据）？用户拒的记进 `edges.md` 了吗？
- [ ] 用户说了"做过 X"吗？技能分是按行为证据走的，还是又拿知识点分凑的？
- [ ] 有需要走 §8 的系统改动建议吗？

## 10.6 反面清单（明确禁止的行为）

> 以下每一条都是这套系统最容易失效的方式。**看到就停手。**

- ❌ **不查档案就开讲** —— 违反 I1，本 Skill 等于没加载
- ❌ **把推断当既成事实讲** —— "你会 React"，实际只是地名推断出来的（违反 I2）
- ❌ **改写或删除 `evidence/` 里的记录** —— 违反 I3，审计链断掉
- ❌ **一次性灌入上百条知识点后不告知** —— 档案瞬间失真且用户察觉不到
- ❌ **把检索到的文章原文贴进档案** —— 档案只存"他知道什么"，不存"网上写了什么"
- ❌ **推断敏感属性**（健康、政治立场、宗教、性取向）
- ❌ **逐条追问推断结果** —— 用批量轻量告知
- ❌ **问了用户却不写入档案** —— 白问一轮
- ❌ **接到系统改进建议就动手改** —— 必须走 §8 五步（违反 I4）
- ❌ **用评判性措辞描述用户水平** —— "你很弱 / 你忘了"（违反 I5）
- ❌ **为了这套系统拖慢回答** —— 查询/写入失败不阻塞回答
- ❌ **没有依据就建议连边** —— 「感觉这两个相关」不是依据；依据必须是共现次数 + 触发的证据/项目
- ❌ **把技能分和知识点分互相换算** —— 一换算 `gap` 恒为 0，这个指标就废了
- ❌ **给没做过的技能打分** —— 「他应该会」不是证据；技能分从 0 起
- ❌ **单次建议超过 3 对，或拒绝后还问同一对** —— 那是骚扰，不是能力
- ❌ **手改 `## 关联` 托管块** —— 它由 `related` 派生，下次同步会被覆盖
- ❌ **往 `graph/` 里塞装不进任何课的东西**（技能、思维方式、流程）—— 这就是 3.4.0 之前那个类别错误
- ❌ **一次把整个 `references/` 全读完** —— 那是把渐进披露又改回单文档；按路由表读当前那件事的那一份
