# 改进系统 · 脚本清单 · 自检与禁区

> **管什么**：用户想改这套系统时怎么走流程、各脚本干什么、每次会话前后自查什么。
> **何时读**：用户对系统本身提改进建议、质疑规则、表达偏好；或会话收尾要自查。
> **读完回**：`SKILL.md` §1 场景路由表。

---

## 8. 系统改进机制

> **一句话原则：先验证，再确认，最后才改。**
> 理由：配置影响**所有已积累数据**，一次草率修改能让整份档案失真，
> 而用户察觉不到——他下次看到报告只会觉得「我怎么变差了」。

### 8.1 先分清：数据问题还是规则问题

| 用户说的 | 属于 | 处理 |
|---|---|---|
| 「这个权重应该调高」 | 直接建议 | 走 §8.2 五步 |
| 「这个判定不对，分数不合理」 | 指出问题 | 走 §8.2 五步 |
| 「凭什么半衰期 90 天」 | 质疑规则 | 走 §8.2 五步 |
| 「我希望报告里能看到 XX」 | 表达偏好 | 走 §8.2 五步 |
| 「这条知识点标错了」 | **数据纠错** | **不走本节**，直接改（`recording.md` §6.5） |

分界线：**改的是一条数据，还是规则本身。** 一条数据只影响他自己，一条权重影响所有历史记录。

### 8.2 五步流程

```
① 复述，确认理解对了
② 判断改动层级，验证可行性
③ 跟用户确认（改什么 / 影响什么 / 怎么回滚）
④ 执行（先留退路）
⑤ 记 CHANGELOG，验证生效
```

#### ① 复述

> 我理解你的意思是：把「自评」的权重从 8 提到 15，
> 因为你觉得自评比系统推断可靠。是这样吗？

不能省——用户说的和你想的经常不是一回事，而改错代价很高。

#### ② 判断层级并验证

| 层级 | 动的是什么 | 风险 | 怎么验证 |
|---|---|---|---|
| **L1 配置** | `_meta/*.md` 的数值 | 低 | 改完跑一次报告对比前后 |
| **L2 数据** | `graph/`、`inference/` | 中 | 在**测试用户**上跑冷启动，看推断结果 |
| **L3 脚本** | `scripts/*.py` | 中高 | 跑完整回归：冷启动 → 录入 → 衰减 → 查询 → 报告 |
| **L4 主逻辑** | 公式、状态判定、流程、**文档结构** | **高** | 必须论证清楚并举例说明影响，充分确认后才动 |

**只能在测试用户上验证**，绝不拿真实用户数据试：

```bash
python3 scripts/init_profile.py --user __test__ --edu "..." --job "..." --region "..."
python3 scripts/report.py --user __test__
# 对比完删掉：rm -rf users/__test__
```

要回答三个问题：典型用户分数会怎么变？有没有副作用？现有数据要不要重算？

#### ③ 确认

必须说清三件事：**改什么、影响什么、怎么回滚。**

> - **改什么**：`_meta/weights.md` 里 `self_report` 权重 8 → 15
> - **影响什么**：你已有的 12 条自评记录会涨 5–8 分，「项目管理」从「理解原理」升到「能上手做」。
>   推断类不受影响。
> - **怎么回滚**：这次改动单独提交一次，`git log` 能看到，你说「撤回」我就回滚那个提交。
>
> 要改吗？

风险越高确认越要充分，L4 必须举出对具体数据的影响，不能只说「应该没问题」。

#### ④ 执行

1. **先留退路**：改动前保持一次干净提交，改完再单独提交。回滚＝`git revert <提交>` 或
   `git checkout -- <文件>`。（只有 git 表达不了的资产，如用户数据快照，才放 `archive/`）
2. 改
3. 跑验证：冷启动 → 录入 → 衰减 → 查询 → 报告
4. 确认无破坏后再告知用户完成

#### ⑤ 记录

在 `CHANGELOG.md` 追加，六项都要有：

```markdown
## [3.0.1] 2026-10-14
- 改动：self_report 权重 8 → 15
- 层级：L1 配置
- 原因：用户认为自评比系统推断可靠
- 影响：已录入自评记录分数上升，推断类不受影响
- 回滚：git 提交 <hash>（回滚即 revert 该提交）
- 验证：测试用户 __test__ 上对比，已触及均值 41 → 44，无副作用
```

### 8.3 这些情况不要动

- 用户只是**抱怨**，没提出方案 → 先问期望，别替他做决定
- 改动会影响所有用户的已有数据 → 必须确认
- 你不确定他想改什么 → 复述再问
- 他随口一说、没明确要求改 → 记下来，不立即执行

### 8.4 主动发现问题的义务

下列情况应**主动提出**（同样走五步，不许自己动手）：

- 同一问题连续 3 次匹配不到知识点 → 骨架缺项或别名缺失
- 某学科知识点长期全 0 分 → 推断模板覆盖不足
- 衰减后出现大量不合理的「生疏了」→ 半衰期档位可能不适合该学科
- 用户反复纠正同类推断 → 推断规则本身可能有偏差
- **某份子文档被反复读取却从不导致动作** → 可能该合回主文档或删掉

## 10.1 脚本清单

| 脚本 | 职责 | 无脚本时 |
|---|---|---|
| `bootstrap.py` | **入口**。检查档案状态，输出下一步动作 | 手工读 `profile.md`（`manual-mode.md`） |
| `init_profile.py` | 冷启动：背景 → 推断 → 铺骨架 → 建档。每个推断分带一条 `role: seed` 证据 | 手工建 `profile.md` 与推断项 |
| `expand_profile.py` | **联网扩展**：把检索到的知识点灌进档案并写证据 | 手工建 points 与 evidence |
| `ingest.py` | 录入证据并重算分数。支持多目标、技能目标、负向证据、`--verify` | 照 `model.md` §3 公式算 |
| `decay.py` | 每日衰减，更新状态与遗忘清单 | 照 §3.3 推算 |
| `query.py` | 提问时查询：知识点状态、横向关联、相关技能、Playbook、画像 | 手工检索 `points/*.md` 的 name 与 tags |
| `report.py` | 知识分布报告：域折叠、广度×深度、待验证清单、技能错位 | 照 `answering.md` §7 八节聚合 |
| `link.py` | **横向边**：共现检测、三档建议、建边/拒边、登记簿 | 手工扫证据找共现（`manual-mode.md` ⑦） |
| `skill.py` | **技能**：播种、新建、连 requires、算错位、记项目与 Playbook | 手工建 `skills/*.md`（`manual-mode.md` ⑧） |
| `migrate_s1.py` | 迁移（3.4.0）：可读文件名 + 字段统一 + 清理旧字段。**幂等，不动分数** | 手工改名与补字段 |
| `migrate_s2.py` | 迁移（3.5.0）：`target_ids` 多值化 + 种子标 `role` + 补录无证据的分 + 合并重名 | 无替代 |
| `migrate_s3.py` | 迁移（3.5.0）：`职业技能` 49 条改归属（**只改元数据，分数零变化**）+ 播种技能簇 | 无替代 |

> 三个 `migrate_*` 是一次性迁移，但都写成幂等，重跑只输出「0 条」。
> 留在仓库是为了让别人也能升级旧档案。

## 10.5 自检清单

**每次回答前**

- [ ] 跑过启动流程了吗（或手工检查过档案状态）？
- [ ] 这个问题该不该查档案？是不是纯事务请求？
- [ ] 拿到知识点状态了吗？**讲解深度是按状态定的，还是凭感觉定的？**
- [ ] 我要说的话里，有没有把 `inferred` 当成「他已掌握」来讲？

**每次会话结束前**

- [ ] 本次触及的知识点，证据写了吗（同一知识点只一条）？
- [ ] 一次回答用到多个知识点时，用了**一条多目标证据**吗（共现才有燃料）？
- [ ] 有新推断项吗？告知了吗？
- [ ] 有暴露遗忘吗？记负向证据了吗？用的是中性表述吗？
- [ ] 有共现候选吗？提建议了吗（≤3 对、带依据）？他拒绝的记进 `edges.md` 了吗？
- [ ] 他说了「做过 X」吗？技能分是按行为证据走的，还是拿知识点分凑的？
- [ ] 有需要走 §8 的系统改动建议吗？

## 10.6 禁区（18 条）

> 每一条都是这套系统最容易烂掉的方式。**看到就停手，不要想「这次例外」。**

**档案可信度**

- ❌ **不查档案就开讲**——违反 I1，等于没加载这套系统
- ❌ **把推断当成事实讲**——「你会 React」，实际只是从城市推出来的（违反 I2）
- ❌ **改动或删除 `evidence/` 的记录**——违反 I3，审计链断裂
- ❌ **一次灌进上百条知识点却不说**——档案瞬间失真且他察觉不到
- ❌ **把检索到的文章原文贴进档案**——档案只存「他知道什么」，不存「网上写了什么」

**推断边界**

- ❌ **推断敏感属性**：健康、政治立场、宗教、性取向
- ❌ **逐条追问推断结果**——用批量告知
- ❌ **问了用户却不写进档案**——白问一轮

**改动系统**

- ❌ **接到改进建议就动手改**——必须走 §8 五步（违反 I4）
- ❌ **用评判的说法描述用户水平**——「你很弱」「你忘了」（违反 I5）

**体验**

- ❌ **为维护档案拖慢回答**——查询或写入失败都不阻塞回答

**连边**

- ❌ **没有依据就建议连边**——「感觉这两个相关」不是依据，依据是共现次数 + 触发证据
- ❌ **单次建议超过 3 对，或拒绝过的还问第二遍**——那是骚扰，不是能力
- ❌ **手改 `## 关联` 那一段**——它由 `related` 生成，下次同步会被覆盖

**概念本身**

- ❌ **把技能分和知识点分互相换算**——一换算错位恒为 0，指标作废
- ❌ **给没做过的技能打分**——「他应该会」不是证据，技能分从 0 起
- ❌ **往 `graph/` 里塞装不进任何课的东西**（技能、思维方式、流程）——
  这是 3.4.0 之前的类别错误，代价是整个骨架失去可比性

**文档**

- ❌ **一次读完整套 `references/`**——等于把渐进披露改回单文档，照路由表读当前那一份
