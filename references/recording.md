# 录入：证据、四类记录、横向边、技能

> **管什么**：用户说了一件值得记的事，把它变成档案里的记录。
> **何时读**：用户说「我做过」「我会」「我一般是」「这条不对」「这两条有关系」，或一次回答结束要落盘。
> **相关**：算分公式在 `model.md` §3；无脚本做法在 `manual-mode.md` §0.8。
> **读完回**：`SKILL.md` §1 场景路由表。

---

## 6.1 录入证据

```bash
python3 scripts/ingest.py --user <id> --target <知识点> \
    --type project_lead --note "主导支付重构"
```

`--type` 决定权重与置信度（对照 `model.md` §3.1）。`--note` 写清**当时到底发生了什么**——
半年后回看，这行字是唯一线索。

忘了知识点叫什么：

```bash
grep -rl "name: 性能优化" users/<id>/points/
```

### 一条证据同时点几个知识点

```bash
python3 scripts/ingest.py --user <id> \
    --target "消息传递机制" --target "谱图理论" \
    --type artifact --note "复现 GNN 过度平滑时，这两个概念同时用到"
```

这是系统最重要的命令。一条证据同时点到 A 和 B 即一次**共现**；
共现攒够了，系统才敢提议「这两条该不该连」。只用单目标，档案永远是一张平铺清单，长不出结构。

### 其它三种用法

```bash
# 记技能：分数进 level，不进 raw_score
python3 scripts/ingest.py --user <id> --skill --target "信息检索" --type project_lead

# 记遗忘：走乘系数，不是加权重
python3 scripts/ingest.py --user <id> --target "傅里叶变换" --type forgot

# 只刷新时间（让 current 回到 raw），不加新证据
python3 scripts/ingest.py --user <id> --target "消息传递机制" --verify
```

### 三个操作细节

- `--target` 接受 **id / 知识点名 / 文件名主干** 三者之一
- **查不到名字时不要猜 id**，先用 `query.py` 或 `grep` 确认
- 提示「未找到知识点」通常是名字不一致（错别字、简称、空格）；按别名对齐，
  **不要顺手新建重复条目**——重复比缺失更难收拾

## 6.2 B 轨：把做过的事记成经验

```
项目       目标、角色、起止、用到哪些能力        ← 必录
  └ 行动   流程、卡点、怎么解的                 ← 有时间就记
      └ 产物  文档 / 代码 / 设计稿 / 报告 / 链接  ← 有就记
```

**只有项目层必填**——要求全填的表最后一定变成空表。

### 记完项目要反过来点亮知识点

叫「反哺」：想清这个项目用到或印证了哪些知识点，生成证据点亮它们。

```bash
python3 scripts/ingest.py --user <id> --type project_lead \
    --target "知识点一" --target "知识点二" --target "知识点三" \
    --note "在 XX 项目里同时用到"
```

项目的 `touched_points` 有几个就 `--target` 几次。做完这一步，经验才真正连到知识上，
否则它只是孤零零一段回忆。

### 攒够两次以上，提炼成 Playbook

同类项目做过 **2 次以上**，可提炼一套 Playbook：适用场景 / 标准流程 / 已知坑位 / 关联知识点。
价值在于下次遇到同类事件直接调流程，不从零推演。

预置 7 个流程模板在 `templates/playbooks.md`（任务拆解与排期 / 优先级判断 / 会议组织 /
文档沉淀 / 复盘方法 / 风险管理 / 求职准备）。

> **模板不是用户的经验**：只有他的项目真跑通了才 `verified_count += 1`，没跑过标已验证等于替他吹牛。

## 6.3 C 轨：他怎么判断事情

两种时机：从多条经验里归纳出共性时；他说出「我一般是…」这类原则性表述时。

| 字段 | 填什么 |
|---|---|
| `statement` | 一句话，要能迁移到别的场景 |
| `domain` | 适用领域，`*` 表示通用 |
| `confidence` | 你有多确信这是他的稳定原则 |
| `source` | `derived`（你归纳的）/ `declared`（他说的） |
| `counter` | **反例或适用边界，必填** |

`counter` 必填的理由：没有边界的原则会变成教条，下次遇到不适用的场景还硬套会出事。
写不出边界说明还没到能提炼的时候，先别记。

## 6.4 D 轨：他是什么样的人

轻量特征卡，**一条只记一个特征，不写人物传记**。

必须区分来源（可信度不同）：`observed` 你观察到的 / `declared` 他明说的。

`observed` 记之前必须问一句：

> 我注意到你更习惯先看例子再看定义，要记下来吗？

他可否认或修正。**连续观察到 3 次以上**才建议记录——一次是偶然，三次才是习惯。

## 6.5 他说「这条不对」

标 `rejected: true`，此后不参与计算、不出现在报告里。**不要删文件**，
保留记录才能回答「当初为什么把这条排除了」。

> **与「改系统」分界**：他说「这条标错了」＝改一条数据，直接改（本节）；
> 他说「凭什么半衰期 90 天」＝质疑规则本身，走 `improving.md` §8。
> 判断标准：改的是一条数据，还是规则。

## 6.6 横向边：两条知识之间的关系

- **纵向边**：域 → 学科 → 课程 → 知识点。由 `graph/` 给出，公共的，所有人一样
- **横向边**：知识点 ↔ 知识点。**个人的**，只能长在档案里

横向边记的只有一件事：**「这两样东西他在同一个场景里一起用过」**。

```bash
python3 scripts/link.py --user <id> --suggest          # 找候选（够格的自动建）
python3 scripts/link.py --user <id> --accept "A" "B"   # 同意建议
python3 scripts/link.py --user <id> --reject "A" "B"   # 拒绝，此后不再问这一对
python3 scripts/link.py --user <id> --add "A" "B"      # 用户自己说这两条有关
python3 scripts/link.py --user <id> --list             # 现有全部边
```

三档，**不要越档**：

| 档 | 条件 | 动作 |
|---|---|---|
| `auto` 自动 | 同属一个域，**并且**共现 ≥3 次 | 直接建。建错可撤销，代价低 |
| `suggest` 建议 | 跨域，或共现 1–2 次 | **先问用户**，同意才建 |
| `manual` 手动 | 用户自己说这两条有关系 | 直接建 |

### 建议必须带依据

> 你在「复现 GNN 过度平滑」那次同时用到了『消息传递机制』和『谱图理论』，
> 这条线要连上吗？（依据：共现 3 次，证据 ev_a1、ev_b2）

- 一次最多 3 对（多了他记不住也答不完）
- 拒绝过的同一对**永不再问**（记录写进 `edges.md`）
- **没有依据不许提**——否则会开始随机连边，随机连出来的图比没有图更糟

### 一条边落在三处，各有各的用处

| 落在哪 | 长什么样 | 谁在用 |
|---|---|---|
| 两端 frontmatter | `related: [对方名字]` | 机器读，这是本体 |
| 两端正文 | `## 关联` 下的 `[[对方名字]]` | Obsidian 靠它画图 |
| `edges.md` | 谁、何时、凭什么连的 / 拒过哪对 | 人查账 |

建边同时写一条 `edge_confirm` 证据，**权重 0**——
「确认相关」推不出「你更懂了」，给它加分是逻辑错误。

> 正文 `## 关联` 由 `related` 生成，包在 `<!-- related:start -->` 与 `<!-- related:end -->` 之间，
> **不要手改**，下次同步会覆盖。

## 6.7 技能：他会不会做

```bash
python3 scripts/skill.py --user <id> --seed        # 铺预置技能簇，熟练度全 0
python3 scripts/skill.py --user <id> --requires "信息检索" --points "信息检索,资料筛选与判别"
python3 scripts/skill.py --user <id> --add "论文复现" --cluster 学术研究 --kind composite
python3 scripts/skill.py --user <id> --list        # 列表，含错位值
python3 scripts/ingest.py --user <id> --skill --target "信息检索" --type project_lead
```

### 两套分数，永不互相推导

| | 靠什么涨 | 存在哪 | 答什么 |
|---|---|---|---|
| 知识点 | `study` / `teaching` / `artifact` | `raw_score` | 他懂不懂 |
| 技能 | `project_lead` / `artifact` / `selftest_pass` | `level` | 他会不会 |

理由：一个人可能「会做但不懂原理」（老师傅），也可能「懂原理但没动过手」（刚读完书的学生）。
这两种人需要的帮助完全相反；若让技能分从知识点分推导，区别就消失了。

### 错位：简历答不出来的指标

```
错位 = 技能熟练度 − 这个技能要求的那些知识点的当前分均值
```

| 错位值 | 说明 | 怎么办 |
|---|---|---|
| **大于 +20** | 手熟但原理淡了，靠手感 | 补原理，多给推导 |
| **−20 到 +20** | 知行相当 | 正常讲 |
| **小于 −20** | 学过没实践，纸上谈兵 | 多给练习，少讲理论 |

简历只能答「你做过什么」，答不了「你手上会的和脑子里懂的是否一致」，
而这个错位恰好决定该补课还是该练手。

`requires` 为空的 `tacit` 技能（说不清依赖什么的手感）算不出错位，
**这是正常状态，不是数据缺失**，不要为凑数硬填。

### 什么情况下才建技能

三条都满足，缺一条就只记经验不建技能：

1. 他**做**过，不只是**学**过（技能分只认行为证据）
2. 有个名字能代表这个能力：要「信息检索」，不要「用 Google 很溜」（后者没法检索也没法对比）
3. 能说清它**依赖哪些知识点**（`tacit` 类除外）

## 6.8 写知识点正文（补「详解」）

**分数回答「你多强」，正文回答「这一条到底是什么」。** 两者必须在同一个文件里——
否则查一条知识要翻两个地方。一页知识点固定是这个形状：

```markdown
# 条目名

## 概要            ← agent 生成：一句话题眼 + 索引（[[#详解]] 能点）
## 详解            ← 内容：它是什么、怎么运转（内部用 ###，不要用 ##）
## 易错点          ← 内容：容易错的地方、易混淆的近邻
## 经验与判断      ← 内容：结论、习惯、判定边界
## 我的掌握        ← 脚本生成（分数、上次接触、证据构成），**不要手改**
## 我的经历        ← 脚本从证据倒出时间线，**不要手改**
## 关联            ← link.py 的托管块
## 更新记录        ← 什么时候补了什么、来源是什么
```

### 什么时候写

| 时机 | 写什么 |
|---|---|
| 回答完一个问题 | 这条的 `详解` 与 `易错点`（讲过的内容不该丢掉） |
| 用户说了自己的做法 | `经验与判断`（他的判断，不是通用建议） |
| 录了一条证据 | 不用动正文，`我的掌握`/`我的经历` 会自动更新 |

### 怎么落盘

```bash
# 看下一批该补哪些：两种排序，按档案状态选
python3 scripts/enrich.py --user <id> --queue --limit 10                 # 碰过的先写
python3 scripts/enrich.py --user <id> --queue --order skeleton --limit 10 # 按骨架顺序铺

# 只看一门课（一门课一次写完）
python3 scripts/enrich.py --user <id> --queue --order skeleton --course 数据库

# 单条写：文件里写 ## 详解 / ## 易错点 / ## 经验与判断，脚本按章节合并
python3 scripts/enrich.py --user <id> --name "异步与事件循环" --md /tmp/x.md --source 用户原话

# 批量写：JSON，键是条目名
python3 scripts/enrich.py --user <id> --batch batch.json
```

**两种排序怎么选**：档案里已经有使用痕迹（有分数的条目）→ `touch`，
先写他真碰过的，写完立刻有「我的经历」对应得上；刚铺开、还没用起来 → `skeleton`，
按门类 → 学科 → 课程 → 条目的顺序铺，与他在 Obsidian 里打开骨架看到的先后一致。
骨架顺序取 `_meta/domains.md` §2 的表序，不是目录名的字典序。

**一次写一门课**（5–10 条），不要跨课程跳着写：同一门课里的条目会互相引用
（写「隔离级别」要能指向「事务与 ACID」），一起写才能把术语和边界对齐。
`--batch` 的每项支持 `summary` / `detail` / `pitfalls` / `lessons` / `source`，
只覆盖传进来的章节，没传的保持原样——可以分几次写，也可以只补一节。

**幂等**：同一份 JSON 重跑，章节内容没变的条目会跳过，不重复追加更新记录。
所以改一条只需改 JSON 里那一条再整批重跑，不必担心把别的条目又写一遍。

### 六段结构（写之前先对号）

`详解` 里的小节按**认知顺序**排，不适用的一段直接不写，不留空标题：

| 段 | 回答什么 | 写到位的判据 |
|---|---|---|
| 它是什么（先划边界） | 别人最容易把它误认成什么 | 能列出 ≥2 个流行误解，并各自说清错在哪 |
| 它解决什么问题 | 没有它会怎样 | 能说出「之前的人怎么做的、痛在哪」 |
| 它怎么运转 | 机制与时序 | 有人问「具体发生了什么」，这节就是答案 |
| 怎么用 | 命令 / 接口 / 参数 | 每条命令都能直接复制执行 |
| 实例 | 一个可复现的具体过程 | 有命令、有真实输出、有一句「这说明了什么」 |
| 与相邻概念的边界 | 最容易混的那几个 | 每个差别都能一句话说清 |

### 排版：让重点自己浮出来

- **三项以上且有对应关系 → 表格**。项目符号只留给「没有对应关系的并列」
- **命令一律进代码块**，块上一行写它在干什么；有输出的贴几行真实输出（哪怕只有两行）
- 最致命的坑用 `> [!warning]`，实例用 `> [!example]`——Obsidian 渲染成彩色块，
  纯文本下就是普通引用，不会坏
- **关键结论单独成行并加粗**，一次只说一件事，不超过两行
- **表格单元格里不许出现半角竖线**，一律写全角 `｜`。命令带管道符时就别放进表格，
  改放代码块——管道必须半角才能执行，而表格容不下半角竖线，两者不能兼得
- 写完自检三问：**有没有一处表格？有没有一个代码块？有没有一处加粗的结论？**
  三个都没有，这篇就是「一片灰字」，用户会判为「写得很一般」

### 素材：图示、公式、图片、音频、视频

**结构与时序优先画 ASCII 图**（放进代码块）。它不进 `assets/`、不占体积、
任何软件都能看、改起来就是改几行字——比截图活得久，也比一百字描述省地方：

````markdown
```
docker CLI ──> dockerd ──> containerd ──> runc
                                           │
                              clone(各 NS) │ ← 造 namespace
                              pivot_root   │ ← 换根
                              execve       │ ← PID 1 诞生
```
````

**什么时候才用截图**：必须看真实界面才能说清的事——报错弹窗、UI 布局、
硬件照片、真实终端里的颜色与输出对齐。**能用 ASCII 表达的关系，不要用截图**。

**公式**用 LaTeX，Obsidian 内置 MathJax，GitHub 也原生渲染——不需要装插件：

```markdown
行内：注意力权重 $a_{ij} = \mathrm{softmax}(e_{ij})$ 由两步得到。

独立：
$$
\mathrm{Attention}(Q,K,V) = \mathrm{softmax}\!\left(\frac{QK^\top}{\sqrt{d_k}}\right)V
$$
```

- 用 `$…$` 与 `$$…$$`，**不要用 `\(…\)` / `\[…\]`**——Obsidian 不认
- `$` 两侧留空格，否则紧贴中文或数字时可能不被识别
- 公式前一句说清它算什么，公式后一句说清每个符号是什么；只贴公式等于没写

**图片**放 `users/<id>/assets/`，用**标准 markdown 相对路径**引用：

```markdown
![cgroup 内存超限后 dmesg 打印的 OOM 记录](../assets/2026-10-cgroup-oom.png)
```

- 文件名 `YYYY-MM-语义名.png`，语义名能看懂内容，不要 `image1.png`
- **alt 文字必写**：图挂了、导出成纯文本时，它是唯一的信息
- 不用 `![[图片.png]]`（Obsidian 专有语法）——档案要能被任何 markdown 软件打开
- 只放自己截的图或有明确许可的图；**不要直接把别人网页上的图拖进来**（版权 + 原图迟早会没）

**音频、视频**标准 markdown 不支持，用内嵌 HTML + 一行兜底链接：

```html
<audio controls src="../assets/2026-10-付费咨询-讲解录音.m4a"></audio>

[听不到就点这里](../assets/2026-10-付费咨询-讲解录音.m4a)
```

- 本地文件优先。**不要嵌 YouTube / B站 iframe**——离线打不开，视频也随时会下架
- 视频同理 `<video controls src="…"></video>`

### 外链：怎么挑一个十年后还能打开的网址

链接是档案里最容易烂的部分。判断标准只有一条：**这个地址是不是「内容标识」而不是「位置」**。
带时间戳、带查询参数的地址记的是位置，改版就废；带编号的地址记的是内容，永久有效。

**按这个顺序选**：

| 优先级 | 类型 | 例子 |
|---|---|---|
| 1 | 永久标识符 | `https://www.rfc-editor.org/rfc/rfc9110.html#section-9.2.1`、`https://doi.org/10.1145/3292500`、arXiv 的 `/abs/` 页 |
| 2 | 官方一手文档 | `docs.python.org/3/library/asyncio.html`、`man7.org/linux/man-pages/man7/cgroups.7.html`、`kernel.org/doc/html/latest/`、`developer.mozilla.org/zh-CN/` |
| 3 | 稳定百科 / 教材 / 标准组织 | 维基百科条目页、W3C `TR` 页、出版社书籍页 |
| 补充 | 个人博客、CSDN、掘金 | **只能当补充**，必须同时给官方源。它们改版、删号、搬迁的概率很高 |

**这些一律不用**：

- 短链：`t.cn` `bit.ly` `dwz.cn`——解析目标随时可变
- 追踪参数：`?utm_source=` `?spm=` `?from=` `&share=`——去参数后的地址才是真地址
- 临时签名：`?X-Amz-Signature=` `?Expires=`——几小时后就 403
- 搜索结果页：`?q=` `?wd=`——下次打开已经不是同一批结果
- `localhost`、`127.0.0.1`、内网 IP——别人打开是空
- 嵌 iframe 的视频/文档——离线失效，且源随时下架

**每条外链必须配一句「它讲什么」**：

```markdown
[RFC 9110 §9.2.1](https://www.rfc-editor.org/rfc/rfc9110.html#section-9.2.1) — HTTP 方法的「安全」与「幂等」定义
```

链接哪天死了，这句话就是重新找到替代来源的唯一线索。一个裸链接等于一条迟早丢掉的引用。

**核对过再写进「更新记录」**：

```bash
python3 scripts/check_links.py --user <id>          # 先看清单，标出可疑地址（不联网）
python3 scripts/check_links.py --user <id> --check  # 发请求核状态码，看有没有搬走、403、DNS 失败
```

写完后在「更新记录」补一行「2026-10-24 补写详解（来源：联网；链接已核对）」。
**链接是别人的资产，会变；核对时间是档案自己的资产，不会变。**

### 长度

一条 **100–350 行**是正常区间。反例要记住：`容器与命名空间` 第一版 96 行、
全是项目符号，被用户判为「写得很一般」；重写到 277 行才到位。
**短不是优点，信息密度高才叫短**——为了短删掉实例和命令，等于把「能查」做成「只能看」。

超过 400 行通常不是文笔问题，是**粒度问题**：这一条里塞了两个可以独立成条的东西，
该拆（`link.py` 拆条 + 补 `related` 边），而不是继续往下写。

### 内容边界（这条别越界）

- `详解 / 易错点 / 经验与判断` 写的是**关于知识本身的内容**，agent 可以写，
  但必须标来源：`通用知识`（自己的知识）/ `联网`（有出处）/ `用户原话`
- `我的掌握 / 我的经历` **只能由证据长出来**。想要这两块有内容，
  就得让用户真的做过、讲过、踩过——脚本会自己更新，手填会在下次录入时被覆盖
- 概要里的「一句话」是**索引的入口**，不是简介：30 字内说清它是什么；
  写不出来通常说明这一条还没理解到能讲的程度
