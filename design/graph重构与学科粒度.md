> 状态：**草案**。D1 / D3 / D4 已定，D2 待定。三件小事已落地（3.7.1）。
> 改动范围涉及 500 条知识点的 `subject` 值，动手前走 §8 五步。
> 关联：`design/项目现状.md` §7 已知瑕疵 / `_meta/domains.md` §3 课程级覆盖

## 1. 要解决什么

现在 `graph/` 是两层：`学科.md` → `## 课程` → `- 知识点`。**能跑，但四处不对**：

| 问题 | 证据 |
|---|---|
| **顶层粒度不一致** | 「计算机科学」是一个一级学科，「人文社科」是哲/史/法/教/经/文六个门类混在一起，「生活常识」压根不是学科 |
| **域映射靠打补丁** | `_meta/domains.md` §3 的 16 条「课程级覆盖」全部是为「人文社科」兜底。域本该一门类对一域，现在要逐个课程声明 |
| **粒度不能按背景调** | `init_profile.py` 选 2–4 个学科后**整学科铺满**。给个「我做前端的」和「我搞 GNN 的」，铺出来的东西一样 |
| **叶节点会变成文件洪水** | 骨架每加一条，用户的 `points/` 就多一个文件。现在 493 条 = 500 个文件，铺到 1200 条就是 1200 个 |

第 2 条是第 1 条的后果；第 4 条是**必须先解决再扩条目**的前提。
所以重构的收益不是「目录更好看」，是**能删掉一层补丁，并且让骨架能长大而用户目录不长大**。

## 2. 目标结构：四层，叶节点不是文件

```
graph/
  信息与计算技术/                      门类  ← 目录
    计算机科学与技术/                  学科  ← 目录
      数据结构与算法.md                课程索引（结构文件，不带 frontmatter）
    人工智能/
      机器学习.md
```

```
users/<id>/points/
  二叉堆的上浮与下沉.md                叶节点  ← 唯一带 frontmatter 的实体文件
  红黑树.md
```

**三个要点**：

1. **深度封顶四层**，叶节点不再往下分。需要更细时把一条拆成两条，不加第五层。
   层数一多，同一深度就会有的装概念、有的装章节，脚本和报告没法统一处理。
2. **知识点只落在叶节点文件里**；中间层可以有文件，但只装结构（索引、说明、清单），
   不装分数、证据和正文。叶节点文件**在被需要时才创建**（铺开或证据命中），见 §7。
3. **跨学科的知识点只建一个文件**，另一个方向写 `→ 见 <课程>` 的引用标记，
   再用 `related` 建立链接。复制两份会让同一件事算两次分，`raw` 就不可信了
   ——这是你说的「优化系统的一种策略」，本质是**用链接换一致性**。

## 3. 门类怎么切（D1 已定：10 域 + 生活常识）

门类 = `_meta/domains.md` §1 那 10 个 ISCED-F 域，再加 `生活常识` 一个非学科门类。

信息与计算技术 ／ 自然科学与数学 ／ 工程、制造与建造 ／ 商业、管理与法律 ／
人文与艺术 ／ 社会科学与信息 ／ 教育 ／ 农业与生命 ／ 医学与健康 ／
服务业与实务 ／ 生活常识

- 「域」这个概念退化成「门类」的别名，少维护一套映射
- §3 的 16 条课程级覆盖**全部删除**——一个课程只属于一个门类，不需要例外
- 现在是 9 个名字，改后 11 个；「计算机科学」「数学」「外语」「艺术与设计」降一级成为学科

### 3.1 生活常识按什么分类

你说的方向是「按场景、时间时代分类」。我的判断是**一半采纳**：

| 维度 | 结论 | 理由 |
|---|---|---|
| **场景** | ✅ 做「学科位」 | 生活常识没有学科，只有情境。「居家 / 出行 / 就医 / 理财 / 法律求助 / 饮食 / 育儿 / 车辆 / 数码」这一层正好顶替「学科」，而且它和用户经历直接对应 |
| **时间时代** | ❌ 不做目录，✅ 做切面 + 衰减档 | 它和场景是**正交**的：任何一个场景里的条目都有时效性（个税起征点、医保报销比例、换证规则）。拿它做分类，同一场景会被切成「旧的/现在的」，每过几年目录就得重排一遍 |

**时效问题用衰减解决，不用分类解决**：

- 新增衰减档 `volatile`（90 天，比 `foundation` 的 180 天更快）
- 条目带 `verified_at`（最后一次核实规则的日期），报告里单列「可能过期」
- 确实想记年代时写进切面 `context: [2026]`，不占目录层

这样「会过期」这件事在每个条目上表达，而不是在目录里表达——目录结构不该因为政策改版而重排。

> 预置场景别铺多：现有 7 条（理财/法律/健康/急救/饮食/出行/生活维修）够用，
> 其余等用户的真实经历带出来。场景写多了又变成「话题清单」。

## 4. 目录与文件怎么分（D2 已定：中间层可建文件，知识点集中在叶节点）

**中间层可以建文件，但只装结构；知识点一律落在叶节点文件里。**

| 层 | 形态 | 装什么 | 装不装知识点 |
|---|---|---|---|
| 门类 | 目录 | — | — |
| 学科 | 目录，可放 `README.md` | 学科范围、与相邻学科的界限 | ❌ |
| 课程 | `graph/<门类>/<学科>/<课程>.md` | 条目清单、课程目标、常见误区 | ❌ 只出现名字 |
| 叶节点 | `users/<id>/points/<知识点名>.md` | frontmatter + 正文 + 证据链 + 链接 | ✅ **全部** |

三条规则：

1. **知识点只有一个家：叶节点文件。** 分数、证据、`related`、正文全在这里；
   叶节点之间用 frontmatter `related: [名字]` + 正文 `## 关联` 的 `[[wikilink]]`
   托管块建链接（Obsidian 图谱只认正文里的 wikilink，见 `references/recording.md` §6.6）。
2. **中间层文件只装结构**，不装分数、不装证据、不装正文。改它不影响任何人的档案。
3. **叶节点文件自带归属**：`category` / `subject` / `course` 三个字段自己说明挂在哪，
   所以**路径可以自由重组，身份不变**——这条是「结构稳定」的落点。

为什么知识点必须集中在叶节点（「结构稳定」的来源）：

门类 / 学科 / 课程的划分**一定会变**——这次重构是一次，G2 还会再拆再并。
如果知识点散在中间层文件里，每改一次结构就要搬一次内容，**搬的过程就是出错的过程**
（3.4.0 改名时 47 个文件被误加后缀，就是这么来的）。
现在知识点自带归属字段，重组结构只是**改字段、移路径**，内容一个字不用动。

代价说清楚：骨架里会有 **67 个课程索引文件**（现在 9 个），
但叶节点实体文件不在骨架里批量预建，只在用户档案里按需生成。
所以仓库侧的增长停在中间层（随学科/课程数），用户侧才随真正用到的知识点增长。

## 7. 叶节点：知识点的唯一落点

这一节改自你的三条要求：**叶节点才建文件**、**叶节点别切太细（文件会爆）**、
**跨学科只给引用标记**。落成五条规则。

### 7.1 判据：三条全满足才是叶节点

1. **单一可验证**——能用一个问题问出「会不会」。
   `泰勒展开` ✅／`矩阵运算` ❌（乘法、求逆、秩是三件可分别验证的事）
2. **单次证据能整体点亮**——一次项目或一次讲解覆盖它，不需要再切。
   `矩阵乘法的手工计算` ✅／`线性代数` ❌
3. **归属唯一**——只属于一个课程。跨课程的选一个**主归属**，另一头写 `→ 见 <课程>`，
   再用 `related` 建链接，**不复制第二个文件**

### 7.2 叶节点文件什么时候创建

叶节点是唯一实体，但**不是一上来就把 493 条全建成文件**——那样用户目录会先被塞满，
里面全是 0 分条目。改成按需创建：

| 时机 | 触发条件 | 结果 |
|---|---|---|
| **铺开** | 学科在 `directions` 里，且条目 `importance >= 1.0`（⭐⭐） | 建一个 0 分叶节点文件 |
| **证据命中** | `ingest.py --target X` 指到骨架里还没建的条目 | 先按骨架元数据（`subject`/`course`/`importance`/`profile`）建 0 分文件，再加证据 |
| **联网扩展** | 检索确认后的方向，落到骨架外的细分条目 | 建文件 + `role: seed` 证据 |
| **手工声明** | 用户说「我要记这个」 | 建文件 |

**「还没建文件」是正常状态，不是缺数据。** 骨架里一行清单足以表达「有这么个知识点」，
用户没碰到它就不需要一份文件——这也是骨架能长得比用户目录大的原因。

**盲区口径要跟着改**：现在盲区是「已铺开但 0 分」，改后必须变成
**「骨架全集 − 已建文件且已触及」**。这要求 `report.py` / `query.py` 能读课程索引，
不能只看 `points/`。**这是本方案的真实成本，不是免费的。**

### 7.3 文件数预算（回答「不好维护」）

| 阶段 | 骨架条目 | 建文件规则 | 用户目录文件数 |
|---|---:|---|---:|
| 现在 | 493 | 全部 9 学科、全部条目 | 500 |
| **G1**（37 学科，条目不变） | 493 | 只建 directions 的 2–4 学科 | **约 150–250** |
| G2 扩到 1200、不做按需创建 | 1200 | 全部铺开 | 1200 ❌ |
| **G2 扩到 1200 + 按需创建** | 1200 | 2–4 学科 + 只建 ⭐⭐ | **约 200–350** |

关键结论：**用户目录的大小由「选中几个学科 × 建了多少 ⭐⭐」决定，不由骨架总量决定。**
所以骨架可以长大，档案不会跟着膨胀——这才是能长期维护的前提。

### 7.4 现有骨架里的真实反例

| 条目 | 问题 | 处理 |
|---|---|---|
| `矩阵运算` | 3 个概念压成 1 条 | 拆（G2） |
| `四则运算与运算律` | 是群组名，不是判断单元 | 拆 |
| `会议管理` / `会议组织` | 同一课程内近重复 | 合并 |
| `时间管理` / `时间精力管理` | 同上 | 合并 |
| `书面沟通` / `商业写作` | 边界重叠 | 择一，另一个做引用标记 |
| `通用职场工具` 21 条 | 课程本身是杂物筐，超过单课程上限 | 拆成「职场沟通 / 商务写作 / 办公工具」三门课 |

### 7.5 规模（D3 已定：先少一点）

测试阶段**不扩张**，G1 保持 493 条。等结构稳定、确认环节跑顺了，G2 再按下面的上下限补：

| 层级 | 下限 | 上限 | 超了说明 |
|---|---:|---:|---|
| 单课程 | 8 | 20 | 少于 8：课程切太粗；多于 20：该拆课程 |
| 单学科 | 40 | 120 | 少于 40：学科还没铺开；多于 120：该拆学科 |
| 全库 | 500 | 1200 | 现在 493，G2 的目标区间 |

**为什么要上限**：骨架是**起点不是全集**，缺的靠联网扩展补（`expansion.md`）。
条目太多会让用户第一次打开就被淹没，也让每日衰减任务变重。

## 8. 学科粒度由背景决定（D4 已定：可以做）

目标你说得很清楚：**背景给得越细，铺得越准**。现在缺的不是目标，是**确认环节**。

### 三档

| 背景精度 | 例子 | 铺多少学科 | 铺多深 |
|---|---|---|---|
| 只有学历/职业 | 「本科」「销售」 | 1–2 门类，2–4 学科 | 只铺 ⭐⭐ |
| **笼统方向** | 「我搞计算机的」 | 该门类下全部学科 | ⭐⭐ + ⭐ |
| **细致方向** | 「做 GNN 推荐系统」 | 1 学科 + 1 个相邻学科 | 全部条目 + 联网补细分领域 |

### 流程改成五步

```
背景输入
  → ① 解析出候选方向清单（门类 / 学科级）
  → ② 回显确认：「我理解你的方向是 A、B，对吗？要不要增减？」  ← 必须有
  → ③ 按确认后的方向联网检索（课程 + 典型条目 + 来源 URL）
  → ④ agent 审阅：去重、对齐骨架命名、剔除教不出来的东西
  → ⑤ 写入：0 分条目 + `role: seed` 证据 + 来源记进 `source_ref`
```

**第 ② 步不能省。** 笼统背景最容易铺错——「我搞计算机的」可能是运维、前端、
算法，也可能只是「会用电脑」。铺错了不体现在分数上（都是 0 分），体现在
**用户第一次打开就看到一堆跟自己无关的东西**，然后他不会再看第二眼。

细致方向也要确认，但要确认到「你说的 X 是不是这个学科」——
「GNN」可能落人工智能，也可能落数据科学，取决于他做的是模型还是工程。

### 留痕

`profile.md` 加两个字段，下次不再问：

```yaml
directions: [计算机科学与技术, 人工智能]   # 确认过的方向
granularity: fine                        # coarse / fine
```
