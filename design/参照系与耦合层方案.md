## 1. 结论摘要

| 编号 | 结论 | 关键机制 |
|---|---|---|
| **P1** | **自建伞层（10 个并列域）+ 切面层 + 伞下挂载权威参照系** | 域为低频、切面为高频，两层分离 |
| **P2** | 耦合**不做成目录，做成图上的横向边** | 纵向边来自参照系（稳定），横向边来自证据与用户（涌现） |
| **P3** | 三类实体（知识 / 技能 / 经验）+ 三类边，经验层组织轴是**情境** | 项目 → 向内反哺 / 向外生成边 / 向上沉淀 Playbook |
| **P4**（本轮新增） | **涌现分层**：个人只提议，判定权在群体与维护者 | 个人层产候选簇，不产学科 |

**三条贯穿全局的设计原则**（本轮的真正产出）：

> **原则 A — 变化频率不同的东西，不放同一层。**
> 目录层（低频、稳定、可比）与切面层（高频、可变、个人化）必须分离。
> 这是用户「这两个域修改频率很高」这个观察直接推出的结论。

> **原则 B — 存储层保持稳定、完整、机械；聚合、折叠、涌现都放展示层。**
> 骨架全铺（保证每个领域都有「位置」）+ 展示层折叠（保证不吵）
> ＝ 取代「删骨架」和「收窄人群」两种错误解法。

> **原则 C（本轮新增）— 权力的高度决定事实的强度。**
> 个人层能产生**候选**，只有群体共识与系统维护才能产生**学科**。
> 学科是集体事实，不是个人声明——这条守住了「量化」的可信度。

**一个横跨全局的前提**：`domain`（域）与 `subject`（学科）都是**自建**的，
参照系只是外挂在它们上面的**标签**。因此——**参照系怎么改版、怎么更换，用户档案一行都不用迁移。**
（这消除了 v0.1 关于「骨架版本化」的讨论：不需要版本迁移，只需要换标签。）

## 2. P1：参照系与伞层

### 2.1 为什么不能直接采用一个现成标准

| 候选标准 | 覆盖范围 | 文化中立 | 到哪个粒度 | 不适用的原因 |
|---|---|---|---|---|
| 中国《研究生教育学科专业目录》 | **仅可授学位的学科** | 低 | 门类 / 一级学科（二级以下自主设置） | 排除职业技能、生活知识；中国特有 |
| 中国《普通高等学校本科专业目录》 | 本科专业 | 低 | 门类 / 专业类 / 专业 | 同上，且与研究生目录重叠 |
| UNESCO **ISCED-F 2013** | 11 领域 / 29 学门 / 约 80 细类 | **高** | 到约 80 细类到底 | 偏「教育项目」；**正在修订**（2025 成立工作组，预计 2027 提交新版） |
| 中图法 / 杜威十进分类 | 图书文献 | 前者低 / 后者西文中心 | 很细 | 为**藏书**服务，不是知识结构 |
| O*NET / ISCO-08 / ESCO | **职业与技能** | 高 | 职业 / 技能 | 是职业不是知识 |
| Wikipedia / DBpedia 分类树 | 极广 | 高 | 极深 | **无权威、无固定层级、持续变动** |

**结论：没有任何一个标准同时满足「覆盖所有人类知识 + 门类稳定 + 文化中立」。**
它们各自服务于不同目的（学位授予 / 图书编目 / 劳动市场统计）。

### 2.2 伞层：10 个并列域

采用 ISCED-F 的 11 个 broad fields，**减去 `00 通用课程`**（理由见 §2.3）：

| # | 知识域 | 对应 |
|---|---|---|
| 1 | 教育 | ISCED-F 01 |
| 2 | 人文与艺术 | ISCED-F 02 |
| 3 | 社会科学与信息 | ISCED-F 03 |
| 4 | 商业、管理与法律 | ISCED-F 04 |
| 5 | 自然科学与数学 | ISCED-F 05 |
| 6 | 信息与计算技术 | ISCED-F 06（与工程并列，独立成域） |
| 7 | 工程、制造与建造 | ISCED-F 07 |
| 8 | 农业与生命 | ISCED-F 08 |
| 9 | 医学与健康 | ISCED-F 09 |
| 10 | 服务业与实务 | ISCED-F 10 |

> 军事领域未单列，由参照系挂载决定。
> ISCED-F 自己也没覆盖「生活知识与技能」——但它**不需要**：生活知识（烹饪、理财、育儿、驾驶、修缮）
> 本来就分布在上述 10 个域里，只是语境不同。用切面表达即可（§2.3）。

### 2.3 切面层：被删掉的两个域去哪了

**关键判断**：「通用与跨域方法」和「生活与实践」**不是并列域，是横切面（cross-cutting facet）**。

- 「通用与跨域方法」不是「和数学并列的一块地」，它是**在所有地上都能用的东西**（批判性思维、科研方法、系统思维）
- 「生活与实践」也不是一块地，它是**所有学科在日常生活中的投影**

把它们建成并列目录会有两个必然结果（用户已诊断出来）：
1. **变动频率远高于其他域**（跨域方法天天在变，数学域几十年不动）→ 目录层不稳定
2. **数量组合爆炸**：「通用与跨领域」下要放所有域两两交叉的方法论，文件数将是其他域之和
   → 单目录查询会崩

**方案：把它们降为切面，不占目录，只在存储上做标签、在展示上做视图。**

```yaml
# 知识点条目上的字段（扁平写法，见 §11.3 修正 2 —— 不嵌套）
domain: 信息与计算技术          # 隶属域（10 选 1，低频）
transferable: 0.8              # 切面① 可迁移性 0–1：这条知识能不能跨域用（高频）
context: [专业, 生活]           # 切面② 适用语境（高频）
```

- 「**通用与跨域方法**」= 视图：`transferable >= 0.7` 的知识点
- 「**生活与实践**」= 视图：`context` 含 `生活` 的知识点

**切面的增删不改变目录结构**——这正是原则 A 的落地。目录层稳定，切面层自由变动。

**「面向所有人」与「含个人成分」不矛盾**：切面的**标签本身是公共知识**
（我们知道「批判性思维」可迁移性高），而**你哪些知识真的被迁移过、迁到哪**属于个人实例。
前者在骨架，后者在边。

### 2.4 与现有 `graph/` 的关系：升格，不是重写

现有骨架的 9 个「学科」已经是伞层雏形，只是粒度不一致（横跨门类、一级学科、非学科四档）。

处理方式：**新增 `domain` 与 `facets` 字段作索引，`subject` 完全不动。**

| 现有 subject | → domain |
|---|---|
| 计算机科学 | 信息与计算技术 |
| 数学、自然科学 | 自然科学与数学 |
| 工程与技术 | 工程、制造与建造 |
| 艺术与设计 | 人文与艺术 |
| 人文社科 | 人文与艺术 + 社会科学与信息 |
| 商业与管理 | 商业、管理与法律 |
| 外语 | 人文与艺术（+ 切面 transferable 高） |
| 职业技能 | **不归任何域**——按实体类型拆到各层（§4.6） |

→ **零数据迁移**。`domain` / `facets` 只是给现有条目贴的索引。

### 2.5 分层铺开，与存量档案的处理

v0.1 曾建议把目标收窄为「知识工作者」，**用户明确拒绝，此处撤回**。
改为**分层铺开**（lazy expansion），让粗细自适应：

| 层 | 是否铺给所有用户 | 量级 |
|---|---|---|
| 域（domain） | **总是铺** | 10 |
| 学科（subject） | **总是铺** | ~100 |
| 课程 | 按需展开 | — |
| 知识点 | 按需展开 | — |

一个厨师拿到的是 10 个域 + 约 100 个学科的轻骨架（不吵），他做菜相关的部分自己长。
一个计算机研究生可以展开到知识点粒度。**同一套骨架，两种深度。**

**存量档案（已铺 492 条）：保持不动**（用户授权本轮决定）。理由三条：

1. 新机制（技能层、横向边、先验字段）**一条都还没验证**，此时改存量等于把两件事混在一起，
   出了问题分不清是机制错还是迁移错。
2. 「存量太吵」这个痛点在**展示层**就能解决（按触及程度折叠），不必动数据。
3. 新骨架规则的验证对象应该是**新用户**（或 `__test__`），不是唯一的真实档案。

唯一的例外：`capability_tags` 的分流需要一次**只读扫描**（只统计、不写入），
看清数据再决定何时执行（§4.6）。

### 2.6 硬约束

1. 伞层与参照系**只作导航**，不预铺知识点、不参与评分
2. **参照系永不写分**——否则等于把公共分类当成个人证据，违反不变量 I2（无证据不写分）
3. 骨架全铺、噪声在展示层解决（原则 B）
4. 评分只来自证据（A 轨）与项目（B 轨）
5. **切面的值也是启发值**，不是分数（§7 同理）

## 3. P2：耦合层 = 图上的横向边

### 3.1 从「目录」改为「边」

用户的方向是对的：**耦合对分类不是必须的，对个人才是必须的。**

分类的本质是**划分**，划分必然切断关系。参照系能给「交叉」一格
（中国目录第 14 门类、ISCED-F 编码 `8`），但**给的是一格，不是一条边**。
v0.1 试图另建一个 `coupling/` 目录来装交叉方向——**这个设计被撤回**，理由：

- 交叉方向一旦成为「目录条目」，就又要回答「它属于哪个域」→ 回到划分问题
- 且数量会随组合爆炸（N 个域两两组合 ≈ N²/2）

### 3.2 同一张图，两种边

```
纵向边（is-a / part-of）   域 → 学科 → 课程 → 知识点      来自参照系，稳定、低频
横向边（related-to / co-occur）  知识点 ↔ 知识点          来自证据与用户，涌现、高频
```

### 3.3 边的四种来源

| 来源 | 机制 | 质量 |
|---|---|---|
| **证据共现**（自动） | 同一条证据同时点亮多个知识点 → 反复共现 → 提示「这两条可能相关，要连吗」 | 中（需确认） |
| **经验引用**（半自动） | 一个项目同时用到跨域知识 → 那些知识之间长出候选边 | 高（有情境支撑） |
| **agent 建议 + 用户确认** | agent 提出、用户拍板（详见 §6） | 高 |
| **参照系导入** | 已知交叉学科（生物信息、认知科学）的既有关系 | 高（但属「已知事实」） |

**第一条是这套系统独有的能力**——任何简历、任何学科目录都做不到「从用户行为里发现跨域关系」。
技术上需要一个前置改动：**证据的 `target_id` 从单值改为 `target_ids`**（一条证据可点亮多条知识）。

### 3.4 已知交叉学科 ≠ 个人的边

用户举例「计算机是数学与电子电路结合出来的」——**这是知识史，且它已经固化了**：
生物信息、认知科学、金融工程今天都有教科书和课程，**它们已经是学科**，可以当
`subject` 层的一个条目处理，不需要特殊机制。

系统需要处理的是两件不同的事：

| | 是什么 | 放哪 |
|---|---|---|
| **已知交叉学科** | 已被学界公认的领域 | `subject` 层（它就是学科） |
| **个人的跨域连接** | 你从 A 域迁移到 B 域的具体关系 | **横向边** |

前者是公共事实，后者是个人资产。**后者才是这套系统的价值所在。**

### 3.5 防滥用

- 一条横向边要么有 **≥2 次共现证据**，要么**用户显式声明**
- 自动共现**只提示、不自动建边**（避免噪声污染图）
- 不做硬阈值判断，只做排序展示（阈值见 §6，且只用于决定「提不提示」）

## 4. P3：三实体模型（知识 / 技能 / 经验）

### 4.1 更正：连接字段的真实情况（先纠正我上一轮的错误）

v0.2 §3.2 曾写「`connections` 与 `related_to` 早在 `_meta/schema.md` 里留了位置，从未落盘」。
核对了 `_meta/schema.md` 全文后，**这句话是错的**：

- `schema.md` 里**根本没有** `connections` / `related_to` / `application` 三个字段；
  它们是上一轮我为了让 schema「看起来完整」而临时加进 `init_profile.py` 落盘逻辑的，
  属于我自己的发明，不是原始设计。
- 真实存在的、与「连接」有关的既有字段是另外四个：

| 字段 | 位置 | 语义 | 现状 |
|---|---|---|---|
| `touched_points: [kp_*, ...]` | B 轨 `experience/actions/` | 一次**行动**触及哪些知识点 | **已定义，从未写入** |
| `touched_points: [kp_*, ...]` | E 轨 `questions/` | 一次**提问**触及哪些知识点 | **已定义，从未写入** |
| `related_points: [kp_*, ...]` | B 轨 `experience/playbooks/` | Playbook 关联哪些知识点 | **已定义，从未写入** |
| `capability_tags: [高并发, ...]` | B 轨 `experience/projects/` | 项目的**能力标签** | **已定义，从未写入**（且是自由文本，未连知识点） |
| `domain` | B 轨 projects / C 轨 wisdom | 领域标签（wisdom 用 `*` 表通用） | 部分使用 |

**更正后的结论更好**：用户问「经验和技能是不是也该和知识点链接」——
**经验的边已经设计好了三条，只是从没被启用过。真正缺的只有一条：技能 → 知识点。**
所以这件事不是「新造一套连接体系」，而是「启用既有字段 + 补一条边」。

### 4.2 三类实体的性质区分

| | **知识** know-what | **技能** know-how | **经验** know-when |
|---|---|---|---|
| 回答什么 | 是什么 | 怎么做 | 在什么情况下怎么做、结果如何 |
| 可命题 | 是，能写进教科书 | 半：步骤可命题，「手熟」不可命题 | 是，但是**叙事**而非命题 |
| 可穷举 | **能**（学科目录就是穷举的） | 能（技能清单可列） | **不能**（情境无限） |
| 衰减 | 快（45 / 90 / 180 / 365 天 / ∞） | **慢**（会生疏，不会忘掉「会」） | **不衰减**（事实不会变成没发生过） |
| 组织轴 | 学科树 | 能力簇（**不按学科**） | **情境** |
| 现有落点 | A 轨 `points/` | 无（散在 `capability_tags`） | B 轨 `experience/`（空） |

这张表解释了两件事：

- **为什么「经验层没思路」**：因为组织轴选错了。知识可以穷举，经验不能，只能按情境索引。
  **B 轨与 A 轨的骨架不该同构**：A 轨是学科树，B 轨是**情境簇**，C 轨是判据列表。
- **为什么技能不能塞进 `graph/`**：技能不按学科组织（「复盘方法」属于哪个学科？没有答案）。
  现有 `graph/职业技能.md` 把它塞进「学科」，就是这个类别错误的来源。

### 4.3 三类边（一张图看清）

```
  知识点 (A 轨)  ──requires──▶  技能 (B 轨)  ──touched──▶  经验 (B 轨)
        ▲                                                      │
        └──────────────── evidence 反哺 ───────────────────────┘
```

| 边 | 方向 | 字段 | 现状 |
|---|---|---|---|
| **① requires** | 技能 → 知识点 | `skills.requires: [kp_*]` | **缺失，本轮新增** |
| **② touched** | 经验 → 知识点 | `actions.touched_points` / `questions.touched_points` / `playbooks.related_points` | **已定义，待启用** |
| **③ touched** | 经验 → 技能 | `skills.experience_ids` ⇄ `projects.skills` | 新设计（轻） |
| **④ evidence** | 行为 → 任意实体 | `evidence.target_type` 增加 `skill` | 小改 |

**技能是这三者里的中转站**：知识是原料，技能是**可执行的能力**，经验是**用技能解决问题的记录**。
所以技能同时向上连知识、向下连经验——它才是连接的核心节点，不是可有可无的衍生品。

### 4.4 技能升格为实体：放哪、怎么存

**放 `users/<id>/experience/skills/`，归入 B 轨，不新增第 6 轨。**

理由：① 五轨结构（A 知识 / B 经验 / C 智慧 / D 行为 / E 问题）是 SKILL.md 的核心叙事，
新增轨要改整个文档结构，代价大于收益；② 技能与经验同源——都是「做出来的」，不是「学来的」；
③ 证据的 `target_type` 加一个枚举值即可接入现有算分与衰减机制。

```yaml
---
id: sk_<8位哈希>
name: 图神经网络工程实现
kind: composite              # composite 可分解 / tacit 隐性手感
requires: [kp_a1b2, kp_c3d4]  # ← 边①：它由哪些知识支撑（composite 才有）
experience_ids: [prj_x1]      # ← 边③：在哪些项目里用过
level: 0                      # 熟练度，**由行为证据独立推进**
last_used_at: 2026-10
profile: durable              # 衰减档位：技能用最长档
evidence_ids: []
---
```

**关键设计：技能的熟练度与所需知识点的分数是两套独立计算。**

- 知识点分（A 轨）= 学习类证据（读过 / 理解 / 推导过）
- 技能分（B 轨 `level`）= 行为类证据（写过 / 独立完成 / 优化过 / 教过别人）
- 两者**不互相推导**，也不取平均

这不是冗余，而是产出**这个项目独有的一个指标**（§4.5）。

### 4.5 错位指标：一个项目独有的产物

```
gap = level(技能) － mean(current_score(技能.requires 的知识点))
```

| gap | 含义 | agent 该做什么 |
|---|---|---|
| **> +20** | 手熟，但原理淡了（凭手感在做） | 补原理、给推导，讲「为什么这样最好」 |
| **−20 ~ +20** | 知行相当 | 正常按 §5 讲解 |
| **< −20** | 学过，但没实践过（纸上谈兵） | 给练习、给动手任务，少讲理论 |

**为什么这个指标有价值**：任何简历都只能回答「你做过什么」，回答不了
「你手上会的东西，和你脑子里懂的东西，是否一致」。而这两者的错位，
恰恰决定了**该给你补课还是该给你练手**——是 agent 最需要知道、又最难猜到的信息。

### 4.6 职业技能的去向：不是「拆到各领域」，是「拆到各层」

用户说「职业技能要拆到各知识领域处理」——这个方向**只对了一半**。
读了 `graph/职业技能.md` 全文（46 条）后发现：它里面混了**五种完全不同的东西**，
所以它不是「该拆到哪个域」的问题，是「该拆到哪一层」的问题。

| 现分组 | 例（原文） | 本质 | 去向 |
|---|---|---|---|
| 思维方式（7） | 第一性原理、系统思考、批判性思维、类比迁移 | **可迁移方法**——不是条目，是知识共享的属性 | 切面 `transferable`（**不建条目**，只作视图） |
| 沟通表达（8） | 结构化表达、跨部门沟通、谈判、倾听与提问 | **人际技能**，多数不可命题分解 | 技能实体 `kind: tacit` |
| 工具与平台（4） | 办公套件、协作平台、AI 工具使用、自动化脚本 | **工具技能**，可分解 | 技能实体 `composite` + `requires` 指向工具类知识 |
| 执行与协作（7） | 复盘方法、风险管理、任务拆解与排期、会议组织 | **流程方法**（有触发条件、有步骤） | **Playbook** |
| 信息处理（6） | 笔记与知识整理、图表制作、信息检索、数据解读 | 三种混在一起 | 按条分流：方法→切面 / 工具→技能 / 知识→域 |
| 职业素养（7） | 行业认知、简历与面试、时间精力管理、压力管理 | 技能 + 稳定行为 | 技能实体，或 D 轨行为特征 |
| 生活技能（7） | 烹饪、急救常识、法律常识、家电维修、财务规划 | 知识 + 技能，**且语境是生活** | 归入对应知识域 + `context: 生活` |

**结论：`graph/职业技能.md` 这个文件应该被清空**，46 条分派到 5 个不同的层。
这不是「换个域放」，而是承认它从第一天起就是个**类别错误**——它把「能力」当成了「学科」。

**执行前提**：先做一次**只读扫描**，产出 mapping（`条目 → 新落点 + 依据`），
交给用户过目后再决定何时执行。**本轮不执行。**

### 4.7 经验层字段设计

**项目条目** `experience/<prj_id>.md`：


**Playbook 条目** `playbooks/<pb_id>.md`（`applicable_when` 是索引键）：

```yaml
applicable_when: 拿到一篇要复现的论文        # ← 情境，索引键
```

### 4.8 三向产出

```
                    项目 (experience/)
        ┌────────────────┼────────────────┐
        ↓ 向内            ↓ 向外            ↑ 向上
   反哺 A 轨          生成横向边         沉淀 Playbook
  (touches → 分)     (domains 跨域)   (情境 → 可复用方法)
```

**为什么经验是横向边的锚点**：经验是**唯一不衰减**的东西。因为「你做过」是事实，
事实不会因时间流逝而变成没做过。而知识会遗忘（A 轨有 45/90/180/365 天衰减档）。

> **横向边挂在经验上，比挂在知识点上更稳。** 知识点会忘，「2026 年做过 GNN × 材料」不会忘。

### 4.9 采集：把门槛降到三句话

- **不做表单**（「请描述项目经历」没人会填）
- **挂在自然对话触发词上**：「我最近在做 X」「这个我踩过坑」「我们团队用了 Y」
- **最小采集三件事**：**做的是什么 / 涉及哪些领域 / 卡在哪**
- 后续通过对话逐步补全

## 5. P4：涌现的判定主体

用户的判断（本轮原话）：

> 「对于个人而言，很难说一个人创造了一个学科，学科这种存在，是需要多数人认可的。
> 对于个人而言，它只能是一个知识边变多了；所谓涌现创造学科，应该是后续维护更新里，
> 对整个系统的改变。」

这个判断**完全正确**，而且它把我上一轮担心的一个风险（「如果个人也能声明新学科，
量化这件事就松动了」）直接从机制上消掉了。落地为权力分层：

| 层 | 权力 | 产出 | 门槛 |
|---|---|---|---|
| **个人** | **提议权** | 候选簇 `status: candidate`：一组高频共现、且现有学科容纳不了的知识点。**仅展示**，不生成条目 | 共现强度排序 top-N |
| **群体** | **统计权** | 多用户间**同构**的候选簇（需用户明示同意 + 匿名化） | 跨用户重复出现 |
| **维护者**（人） | **判定权** | 是否新增学科条目 | 判据见下 |

**判据（沿用上一轮留下的标准）**：**学科的标志不是「有若干知识点」，而是「有自我叙述的体系」。**

**为什么这个设计稳**：

1. 个人档案里永不出现「个人发明的学科」——学科不会因为某个用户连了几条边而诞生（原则 C）。
2. **新增学科不改用户已有条目**，只是多了一个容器 → 这正是「初始化一次即部署」的另一半：
   **骨架的更新走系统发布，不走用户手动迁移。**
3. 它同时解决了「5 年一修」担忧的剩余部分：门类层几十年不动（用户已判明），
   而新东西长在**扩展区**；等到扩展区的东西被共同体认可，由维护者提升为正式学科。

## 6. 连边的确认机制

用户确认的方向：**手工连应由 agent 产生建议，用户确认后再建立链接。**
在此之上补三条规则，否则会退化成噪声或骚扰：

### 6.1 三档

| 档 | 条件 | 动作 | 标记 |
|---|---|---|---|
| `auto` | 同域 **且** 共现 ≥3 次 | 自动建边，可撤销 | `origin: cooccur` |
| `suggest` | 跨域，或共现 1–2 次 | **agent 建议 + 用户确认** | `origin: confirmed` |
| `manual` | 用户主动声明 | 直接建边 | `origin: user` |

### 6.2 建议必须带依据

```
你在「论文复现：GNN 过度平滑」里同时用到了
『消息传递机制』和『谱图理论』，这条线要连上吗？
```

**没有依据不许建议**——否则 agent 会开始随机连边。依据就是可引用的：
共现次数 + 触发的经验条目 ID。

### 6.3 防骚扰

- **单次建议 ≤3 条**，且必须能一次答完（同意 / 不同意）
- 用户拒绝同一对边 → 记入 `rejected_edges`，**同一对不再建议**
- 建议只在不打断主线的时候提（回答结束后，不插在回答中间）

### 6.4 建边本身也留证据

确认一条边时，写一条低权重证据（`type: edge_confirm`）。
这样「这条边是谁什么时候确认的」也可追溯，与 append-only 证据层一致。

## 7. 先验与逼近：从背景推断到实测收敛

用户的原则（本轮原话）：

> 「所有的初始值，就按照普适性的、用户的背景信息来确定，
> 在与用户的相处当中，一步步逼近用户的真实知识与经验反映。」

### 7.1 系统缺的不是收敛公式，是「显式的先验」

现在系统用 `raw_score = 0` 表达「没触及」，但用户论点点破的是**先验概率**：
「学计算机的人有一定几率了解法律」。这两件事必须分开存：

| | 是什么 | 来源 | 是否参与算分 |
|---|---|---|---|
| `raw_score` | **实测掌握度** | 证据 | **是** |
| `prior_exposure`（新增） | **接触概率**：high / medium / low / minimal | 背景推断 | **否，永不** |

### 7.2 先验的唯一用途：待验证清单

先验不进公式，只用于**排序**，产出一份 agent 的提问弹药：

```
「你没记录过，但按你的背景，这些你大概接触过——有吗？」
   · 数据合规（法律 × 技术）
   · 学术英语写作
   · 科研伦理
```

**这才是骨架全铺真正发挥价值的地方**（回应原则 B）：
否则未触及的知识点就只是 492 行沉默的 0 分，用户永远不知道那里有个位置。

### 7.3 收敛规则

- 某知识点**一旦产生 ≥1 条实测证据** → `prior_exposure` 退为背景信息，
  不再是「待验证」，也不再出现在清单里
- 从未被验证的 `origin: inferred` 条目 → 报告里**单独一栏「待你确认」**，
  与实测分数**视觉上分离**（避免推断分被误认为真实水平）
- 先验永远是**猜测**，任何展示都必须标注它是推断值

这实现了用户说的「一步步逼近」：先验负责**开局不空**，证据负责**逐步修正**，
而两者在数据结构上从不混淆。

| `touches` 嵌套三元组 `[[id, 名, 权重]]` | 扁平 `touched_points: [名字]`，权重走证据条 | 轻量 frontmatter 解析器读不了嵌套结构，而为了这个引入 YAML 库不值 |
| `skills.experience_ids: [prj_id]` | `experience: [项目名]` | 同上：可读性优先，id 仍是每条实体的主键 |
| 种子分「在证据里记 weight」 | **`role: seed`**：直接赋值、只在 `raw=0` 时生效、置信度固定 1.0 | 不显式区分的话，两条 50 分种子会被边际累加成 75，凭空造分 |

## 10. 风险与保留意见

1. **伞层自建 = 又造了一个分类体系**，有重蹈「完备性幻觉」的风险。
   缓解：10 个、只作导航、不预铺、不评分（§2.6）。两个高风险域已降为切面。

2. **多参照系 = 映射成本乘以表数量**。缓解：一张主表必填 + 附加表选填。

3. **参照系与切面永不能影响分数**（已确认为硬约束，§2.6）。

4. **横向边的冷启动问题**：证据少时图很稀，用户看不到价值。
   缓解：S2 时用已知交叉学科做初始填充；共现达 2 次即提示，不等大样本。

5. **新增技能实体 = 多一套要维护的东西**。缓解：S3 才做，且先只启用
   `requires` 与行为证据两个最小功能；`kind: tacit` 的技能允许 `requires` 为空。

6. **职业技能分流是一次破坏性整理**（46 条要清空重分派）。
   缓解：先做只读 mapping 交用户过目，且分流只影响骨架、不影响任何用户分数。

7. **五期内容同上的复杂度风险**。缓解：严格分期，每期独立跑通再进下一期。

8. **SKILL.md 体量**（41KB / 888 行）：采纳渐进披露——主文档只留触发条件与一句话动作，
   细节下沉到 `taxonomy/README.md`、`design/`；单文档部署（模式 B）自动降级。
   **警告：v0.3 又加了三个机制（技能层 / 连边确认 / 先验），若不渐进披露会直接破 60KB。**

## 11. 外部可读性与 Obsidian 兼容

### 11.1 硬约束（用户确立）

> 「我们这个项目，生长出来的纯文档数据是**可以直接看的**，
> 我们也可以**通过 Obsidian 等软件，看出其知识分布情况**。」

这条把「存储格式」从一个实现细节升格为**验收标准**：
档案不只是给脚本读的，它同时是一份**人可以用通用工具翻阅的知识地图**。

### 11.2 只读推演：现状与该约束的实质差距

对 `users/default/points/` 做了一次只读扫描（未写入任何文件），结果：

| 项 | 实测 | 在 Obsidian 里的后果 |
|---|---|---|
| **文件名** | **502 / 502 全部是 `kp_<8位十六进制>.md`** | 图谱里是 502 个乱码节点，**读不出任何内容** |
| 名称含文件系统非法字符 | **15 条**（`I/O 与中断`、`HTTP/1.1 与 HTTP/2`、`CI/CD`…） | 直接当文件名会失败，必须替换 |
| 重名 | **2 类**（`谈判`、`汇报与演讲`，均为「职业技能」×「商业与管理」跨学科重名） | 文件名冲突 |
| 字段覆盖 | `status` 99/502；`connections`/`application`/`related_to` 14/502 | 字段不齐，查询会漏 |
| 嵌套结构 | 若按 §2.3 写 `facets:` 嵌套 | Obsidian 属性面板/Dataview 读不到一级字段 |

> **结论：不做处理的话，这份档案在 Obsidian 里既读不出内容，也看不出分布——**
> 与 §11.1 的硬约束直接冲突。好消息是**改造成本极低**：
> 脚本不依赖文件名（`id` 一律取自 frontmatter 的 `id` 字段），重名仅 2 类。

### 11.3 五项设计修正

1. **命名可读化**：知识点文件名 = `知识点名.md`（不再用哈希）。
   → Obsidian 里直接显示中文名，图谱天然可读。
2. **字段扁平化**：取消 `facets:` 嵌套，`transferable` / `context` 提为一级字段。
   → Dataview 可写 `WHERE transferable > 0.7`；嵌套则要先 `facets.transferable`，且属性面板不展开。
   本项**覆盖 §2.3 的写法**（§2.3 保留概念表述，落地字段以本节为准）。
3. **横向边 wiki 化**：边存为 `[[知识点名]]` 而非 `kp_xxx`。
   → Obsidian 图谱**直接画出边**，零插件；哈希 id 则画不出来。
   （代价：改名会断链。缓解：改名前先全库替换引用，见 §11.7。）
4. **清理发明字段**：删除 v0.2 误加的 `connections` / `application` / `related_to`
   （§4.1 已更正其来源），避免与将来的横向边字段混淆。
5. **知识点平铺**：全部留在 `points/` 一级，**不按域/学科分目录**（现状已是如此，此项为**锁定**）。

### 11.4 为什么必须平铺，不能按域分目录

看起来「按域分目录」更整齐，但会**同时破坏两件事**：

1. **会切断横向边**：Obsidian 的 `[[名称]]` 链接**不含路径**。
   一旦同名条目分散在不同目录，链接即歧义——而跨域正是横向边存在的全部理由。
   把文件按域分开，等于在**文件系统层面**预先否决了「跨域」这件事。
2. **会让「域」变成硬分区**：违反原则 A（域是**低频导航标签**，不是目录结构）。
   域一旦成为目录，改域就要搬文件——又变回「迁移」。

**结论：组织靠字段与边，不靠目录。** 目录只分「轨」（`points/` `evidence/` `experience/`…），
域/学科/切面一律做字段。

### 11.5 命名冲突的处理规则

| 情况 | 规则 | 例 |
|---|---|---|
| 含 `/ \ : * ? " < > \|` | 替换为全角 `／ ： ＊ ？ ＂ ＜ ＞ ｜`（`\` 用 `＼`） | `HTTP/1.1 与 HTTP/2` → `HTTP／1.1 与 HTTP／2.md` |
| 长度 > 60 字符 | 截断 + `…`（macOS 上限 255 字节，中文 3 字节/字） | — |
| 跨学科重名 | 追加 `（学科）` 后缀 | `谈判（商业与管理）.md` |
| 名称首尾空白/末尾句点 | 去除（Windows/SMB 共享会截断） | — |

> **本轮不合并重名的数据，只做消歧。**
> 理由：`汇报与演讲` 两条分数不同（30 与 50），合并需要一次「分数取舍」决策；
> 而「职业技能」整块**即将在 S3 被分流**（§4.6），此刻合并等于马上去拆。
> 消歧是零风险的，合并不是——**分开做**。

### 11.6 S1 迁移清单（一次做完）

以下五件事**操作对象是同一批 502 个文件**，分开做就是五次全量重写，所以合并为一次：

| # | 动作 | 说明 |
|---|---|---|
| ① | **命名可读化** | `kp_hash.md` → `名称.md`，按 §11.5 处理非法字符与重名 |
| ② | **补字段** | `domain`（按 `_meta/domains.md` 映射）/ `transferable` / `context` / `prior_exposure` / `status` |
| ③ | **删发明字段** | 移除 `connections` / `application` / `related_to` |
| ④ | **重名消歧** | 见 §11.5，仅改文件名不加后缀以外的东西 |
| ⑤ | **展示层改造** | 报告：按域折叠 + 广度×深度二维画像 + 待验证清单（`report.py`） |

**执行顺序**（§8 五步）：

```
① 验证   在 __test__ 用户上跑通 init → migrate → report
② 确认   用户已确认（「现在开始修改吧」）
③ 备份   tar 打包 users/default → archive/default-migrate-pre-3.4.0.<日期>.tar.gz
④ 改     跑 migrate_s1.py（先用 --dry-run 看对照表，再正式跑）
⑤ 验证   diff 前后分数与证据条数，必须完全一致
```

> **迁移脚本只做「重排与贴标签」，不碰任何分数、证据、`raw_score`、`peak_score`。**
> 唯一允许的变化是文件名与新增字段——这是一条自检红线。

### 11.7 幂等与回滚

- **幂等**：脚本以「当前状态」为输入而非「上次运行结果」——
  文件名已是可读名的跳过；字段已存在且非空的跳过。**重复运行结果相同。**
- **回滚**：`tar -xzf archive/default-migrate-pre-3.4.0.<日期>.tar.gz -C users`
  可完整还原（含文件名与内容）。系统代码的改动走 git（`git revert`）。
- **对未来的意义**：脚本按 `users/<id>` 参数化，**任何用户升级都能复用**，
  不是一次性的数据手术。
